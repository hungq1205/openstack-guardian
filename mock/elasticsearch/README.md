# Mock Elasticsearch (IAAS API gateway logs)

A local single-node Elasticsearch, seeded with `mock-logs-23.csv` (a real Kibana
Discover CSV export of IAAS API gateway logs), for exercising `cmp_logs_mcp`
against a real-shaped index instead of `httpx.MockTransport` fakes.

## Setup

```bash
docker compose up -d
# wait a few seconds for Elasticsearch to become healthy, then:
python seed.py
curl localhost:9200/iaas-api-2026.08.23/_count
```

`seed.py` drops and rebuilds the index from scratch every run (disposable
local data, not something to accumulate) -- re-running it is always safe.
Pass `--es-url`/`--index`/`--csv` to point it elsewhere; see `python seed.py
--help`.

Then point `cmp_logs_mcp` at it:

```bash
export CMP_LOGS_ES_URL=http://localhost:9200
export CMP_LOGS_ES_INDEX=iaas-api-*
```

A second day, `mock-logs-22.csv`, seeds the same way into its own dated index:

```bash
python seed.py --index iaas-api-2026.08.22 --csv mock-logs-22.csv
```

Guardian's own `cmp-logs` connection (admin GUI's MCP Servers page) uses the wildcard
`iaas-api-*` rather than one literal dated index, precisely so both days are visible at once --
`{base_url}/{index}/_search` is a real Elasticsearch multi-index search when `index` is a
pattern, same convention `openstack-logs`' `OS_LOGS_ES_INDEX_PATTERN=flog-*` already uses. Seed a
3rd day the same way (its own `--index iaas-api-2026.08.<day>`) and it joins the same pattern with
no config change.

## GUI (Kibana)

`docker compose up -d` also starts Kibana at **http://localhost:5601** (no
login -- security is disabled, same as Elasticsearch). First time in, create
a data view (Stack Management -> Data Views -> Create data view): index
pattern `iaas-api-*`, time field `@timestamp`. From Discover you can then
browse/filter the seeded documents visually -- e.g. `level: ERROR` to jump
straight to the one incident, or `request_id: "df3daa616eb14781866673d4c67d062e"`
to see its full cascade across levels.

Kibana takes ~15-30s after the container starts before `/api/status` reports
`available`; `seed.py` only talks to Elasticsearch directly; so Kibana isn't
required for seeding, just for browsing afterward.

## What's actually in here

`mock-logs-23.csv` is one continuous ~3.4-minute burst
(`2026-08-23 23:26:37`-`23:30:00`) of IAAS API gateway logs across 3 hosts
(`iaas-1/2/3`), 14,856 rows. 83% are healthy `log.response` access-log lines
(mostly 200s across `/api/v1/vbs`, `/api/v1/vos`, `/api/v1/svaas`), ~16% are
one repeated harmless deprecation warning, and there is exactly **one**
ERROR: a request for a volume UUID that doesn't exist
(`cinderclient.exceptions.NotFound`, HTTP 404), whose gateway correlation id
(`df3daa616eb14781866673d4c67d062e`) ties together an INFO access-log line, a
WARNING, and the ERROR itself.

`mock-logs-22.csv` is the previous day's equivalent export (`2026-08-22`,
14,846 rows) -- same shape, same one `cinderclient.exceptions.NotFound`
ERROR (different request id, same missing volume UUID). Its only purpose is
**noise**: real-looking background traffic around the mock CMP server's own
scripted incidents (`mock/cmp_server/`, its 3 `ERROR celery.server_creator
...` scenarios) so an agent searching cmp-logs sees a realistic haystack --
tens of thousands of ordinary access-log lines and deprecation warnings, not
an index that suspiciously contains only the incident being investigated.
Both days combined (plus whatever the mock CMP server has logged) is what
`iaas-api-*` actually searches.

`seed.py` parses the raw `log` text into structured fields
(`level`/`logger`/`request_id`/`method`/`path`/`status`/`duration_ms`/
`client_ip`/... -- see the script for the exact schema) rather than indexing
the free-text line as-is, so `cmp_logs_mcp`'s tools can filter/aggregate on
real fields, not just grep the message text.

**Two different "request id" concepts appear in this data -- don't conflate
them:** the bracketed gateway correlation id (`[df3daa61...]`, indexed as
`request_id`, what `follow_request_id` searches on) is generated by the
gateway itself per HTTP request; the `Request-ID: req-...` text inside the
ERROR message is a *different*, OpenStack/cinderclient-generated id and is
not indexed as its own field -- it only exists as a substring inside
`message`/`raw_log`.

**This index has no `server_id`/`task_id` fields.** `cmp_logs_mcp`'s
`search_logs` tool queries this same index by free-text phrase match, so it
works fine here -- but if a *different*, celery/server_creator-worker-shaped
log source is ever added, it will need its own index/config, since nothing
here carries those fields.

## Verified

`docker compose up -d` + `python seed.py` has been run end to end against a
real container (image `docker.elastic.co/elasticsearch/elasticsearch:8.19.20`
-- confirmed to exist and pull cleanly, despite looking suspicious on paper).
All 4 `cmp_logs_mcp` tools were exercised through a real MCP subprocess
against the seeded index and returned exactly the expected results (5 hits
for a free-text UUID search, 3 for `follow_request_id` on the incident's
correlation id, 21 anomalies with default noise exclusion vs. 200 with it
off, 1 for a `status=404` filter).
